Keptstack assesses and sets up local AI systems for businesses with a specific workflow that benefits from running on hardware they control.

KeptstackBusiness model

Assess one workflow. Install only if local wins.

Keptstack assesses one business workflow, installs a local system only when the test supports it, hands over an environment the customer owns, and offers optional care after handover. Pursue a job only when the workflow has a clear local advantage; otherwise recommend cloud.

What is sold

Buyers pay for a mapped working environment, a tested workflow, retrieval and access rules that work on their material, a documented handover they own, and optional maintenance. They are not paying for a runtime they could install themselves.

How money comes in

Revenue comes from paid assessment, implementation, later expansion work and optional care. Care must stay bounded. If support turns into unlimited tickets and answer-quality disputes, the recurring model stops working.

Why the customer still owns it

The ownership claim only works if Keptstack avoids unnecessary lock-in.

Customer data stays separate

Business documents and backups should not be trapped inside one interface or runtime.

Components can be replaced

Ollama, llama.cpp, MLX or another runtime can be changed if licensing, pricing or support changes.

Support is optional

Stopping the care plan should not disable the system. Keptstack is paid to maintain it, not to unlock it.

What would falsify the idea

  • Cloud is often good enough.If most qualified customers are better served by existing cloud products, the addressable market is too small.
  • The DIY setup is cheap.A local runtime and browser interface are no longer scarce. Keptstack has to earn its fee through testing, retrieval design, access and backup rules, update policy, handover and the option to decline the install.
  • Local models may not match the quality customers expect.Each use case needs testing before hardware is sold or installed.
  • Support can become labour-heavy.The business needs standard builds and clear support boundaries or monthly care fees will be eaten by service time.
  • Security expectations can exceed a small provider's capability.Higher-risk work may require specialist partners, formal controls or a narrower scope.
Prototype business model. Pricing, demand and support effort still need validation through real customer discovery and pilots.

The delivery path

Each engagement follows the same sequence. The build only happens after the environment map and workflow test support it.

  • 1. Map the environment.Inspect the document store, current tools, access rules, shadow AI use and what must not leave the business.
  • 2. Test the workflow.Run labelled questions on the approved material, including questions where the correct response is “not found”.
  • 3. Compare and decide.Proceed locally only when one workflow has a clear local advantage and the quality test passes. Otherwise recommend cloud or stop.
  • 4. Build the smallest system.Configure only the hardware, model runtime, retrieval and access needed for the first job.
  • 5. Hand over.Provide the working environment, admin access, documentation, backup notes and the agreed system boundary.
  • 6. Optional care.Maintain the supported build inside the written care boundary. New workflows remain separate projects.

The first workflow

The first build is deliberately narrow. It focuses on document search and drafting because those tasks are easy to test against agreed source material.

Search selected documents

Staff ask questions across an approved document set and receive answers with source references.

Draft from the same material

Staff can prepare first drafts or summaries using retrieved source material, with a person checking the result before use.

Run a quality test first

Keptstack tests the workflow on sample questions before recommending hardware or installation.

Keep later features out of the first build

Transcription, voice and a general high-frequency assistant only proceed if the hardware and business task justify them.

Map the working environment first

The assessment starts with the systems staff already use and the information they are allowed to access. This is a short, written scope, not a full enterprise architecture review.

Document store

Identify the approved corpus and where it lives: SharePoint, file server, iManage, Google Drive, shared drives or controlled exports. The scope is a defined collection, not “all of IT”.

Tools already in use

Record Word, Teams, Copilot, ChatGPT, Claude, Grammarly, browser plugins and any other AI staff already use. The local workspace has to fit beside those tools or staff will ignore it.

Identity and access

Map who may query which document set. The local system should follow the business's existing permission model rather than create a separate access scheme.

Current shadow use

Identify where confidential material is already being pasted into public AI tools. A local alternative only helps if the current behaviour changes.

Controlled-system boundary

Write down what the local model may see and what it must not. Use allow-listed sources. Do not crawl the whole network or unmanaged mailboxes.

Two controls, not one

Stop public AI tools reaching the confidential corpus through policy and suitable technical controls, while also stopping the local system from reaching anything outside the approved source list.

The assessment output includes this environment map and the written boundary. Anything broader becomes a separate architecture or security engagement.

Safeguards

The local system only sees approved documents. It should not crawl the rest of the network or unmanaged mailboxes. Keeping confidential material out of public AI tools is a separate control, handled through policy and appropriate browser or network controls. The local box does not enforce that on its own.
